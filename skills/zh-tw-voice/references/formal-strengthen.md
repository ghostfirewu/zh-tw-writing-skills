# 正式文體的補強範圍

> 用在：場合判成「正式」（報告、提案、對外信件、新聞稿、履歷、產品說明），而作者的原稿或習慣寫法不適合這個文體時。
> 書稿、譯稿（作者的作品）不在此列，照 `zh-tw-anti-slop` 的規則只標注、不逕改。

## 1. 可以補的：說法與結構

| 項目 | 原稿（虛構例） | 補強後 |
|---|---|---|
| **結論放前面** | 先講三段背景，最後一句才說「所以建議延到下季」 | 第一段就寫「建議延到下季」，背景移到後面當理由 |
| **一段一個主旨** | 一段裡同時講預算、人力、時程 | 拆成三段，每段第一句講該段的重點 |
| **拆長句** | 「因為供應商延遲交貨所以測試順延然後上線也跟著延後但行銷活動已經排定了」 | 「供應商延遲交貨，測試因此順延，上線也跟著延後。但行銷活動已經排定。」 |
| **補主詞** | 「已經處理了，下週會再確認。」（誰處理？誰確認？） | 主詞在上下文找得到就補；找不到就問作者，不要猜 |
| **收掉口語** | 「這方案真的蠻扯的啦」 | 「這個方案的成本估得太低」：要改成作者在別處已經講過的具體理由；沒有理由就問作者，不要自己補 |
| **改錯字、統一用詞** | 前面寫「客戶」後面寫「顧客」，指的是同一群人 | 統一成一個 |

`身分` 類的特徵照樣保留：作者自稱「我」，正式信件也可以用「我」；作者習慣先講結論，正好符合正式文體。

## 2. 不能補的：內容

- **事實、數字、案例、引語**：原稿沒有就不加。報告缺數據，標出來問作者，不要寫「預計可節省三成成本」。
- **立場與理由**：作者只說「不建議」，沒說為什麼，就問，不要替他想理由。
- **語氣強度**：口語的「真的很扯」收成正式說法時，不要順便把強度改高或改低。「很扯」是強烈的負評，收成「值得商榷」就是改低了；比較接近的是「明顯不合理」。

缺的內容用 SKILL.md 第 1 節的訪談補。改寫別人的稿子時，改完照跑 `zh-tw-anti-slop` 的 `rewrite_diff.py`，確認沒有加料。

## 3. 怎麼跟作者說

只講文體合不合，不評論程度：

- ✅「報告的讀者會跳著看，所以把結論移到第一段。」
- ✅「這句在貼文裡很自然，放進提案會顯得太隨意，我收成比較正式的說法。」
- ❌「你的句子太長了。」
- ❌「這段寫得不太好，我幫你重寫。」
